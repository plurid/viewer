# Trash and Applications

The sidebar's Applications button opens `/Applications` on macOS, the configured Program Files directory on Windows, and `/usr/share/applications` on Linux. It browses the directory; it does not claim to aggregate all installed applications.

Trash opens a dedicated folder-style browser, named Recycle Bin on Windows. It supports browsing trashed folders, selection, filtering, sorting, scoped Quick Look, Get Info, Copy Path and Restore/Restore to…. Its items remain isolated from generic writable-folder commands. macOS reads the actual user's `.Trash` and mounted-volume `.Trashes/<uid>` folders. Linux discovers the home and mounted-volume locations defined by the [freedesktop Trash specification](https://specifications.freedesktop.org/trash/1.0/); original locations come from checked `.trashinfo` files. Windows enumerates the [Shell Recycle Bin namespace](https://devblogs.microsoft.com/oldnewthing/20140421-00/?p=1183). No individual permanent removal action is offered.

At the root, the title appears once; Back and breadcrumbs appear only inside a trashed folder. Name toggles natural A–Z/Z–A ordering by pointer or keyboard. Original location, date and size headers also sort; unknown metadata stays last in either direction. Original-location cells show the containing folder or Unavailable. Selecting one item exposes its complete, selectable, wrapping original path and **Open original folder in plane**; the same navigation is available in context actions and Get Info. A missing original parent produces an error without closing Trash or restoring anything.

macOS original paths come only from identity-matched Viewer Trash receipts. Items moved to Trash by Finder may have no verified original location; Viewer explains this and offers Restore to… without guessing. The read-only native bridge retrieves the public [date added to directory](https://developer.apple.com/documentation/foundation/urlresourcevalues/addedtodirectorydate) key for verified top-level regular files and folders. This is labeled **Date added**, distinct from a recorded deletion time, and never substituted with modification/change timestamps. The optional, bounded cache cannot authorize an operation. An entirely unavailable date column is omitted; Get Info explains missing metadata. macOS added dates are not inherited by nested children. Supported recorded deletion dates on other platforms retain their distinct semantics.

Restore checks the selected item's identity/version and Trash confinement, then preflights the existing destination parent, disk and collision state. It never replaces or merges existing items, recreates missing parents, follows symbolic-link ancestors or falls back to copy-and-delete. A cross-disk destination is refused. macOS uses the coordinated exclusive-rename adapter; Linux retains orphan `.trashinfo` metadata rather than permanently deleting it. Generated private-root native tests establish the local macOS adapter behavior, not positive restore from the owner's system Trash.

The inventory checks private ownership, permissions and canonical roots. It never follows a Trash-root symlink. Missing roots are skipped; unreadable roots are reported as unavailable, not empty. The list is capped at 4,000 visible items and virtualized. Partial or unreadable inventories disable emptying. Reading and refreshing never call removal. macOS requires Full Disk Access to enumerate system Trash; a folder picker cannot grant this privacy permission. Privacy denial explains System Settings → Privacy & Security → Full Disk Access, enabling Viewer and restarting it. Open Privacy Settings… opens a fixed settings URL only; Viewer does not grant permission or widen agent scopes. [Apple's macOS security guidance](https://developer.apple.com/videos/play/wwdc2019/701/?time=1995).

App Sandbox file authorization is independent of Full Disk Access. An explicit `FILE_ACCESS_REQUIRED` result offers the exact private Trash folder picker, with hidden folders shown and Command-Shift-G path instructions; choosing a different folder never grants it. Unverified/symlink roots offer no access action. Genuine signed Store access remains unqualified. Apple documents that [Trash URLs differ in an App Sandbox](https://developer.apple.com/documentation/foundation/url/trashdirectory); Viewer does not substitute the container's Trash for the user's system Trash.

The dedicated renderer interface contains `trashList`, `trashAccess`, `trashPreview`, `trashCopyPaths`, `trashRestore` and `trashConfirmation`. These context actions are not published as agent commands. `trashConfirmation` displays native UI only: it accepts the reviewed inventory revision, not paths, an actor, an approval flag, an empty operation or a callback. No `emptyTrash`, erasure/approval IPC, command registration, shortcut, MCP tool, recipe or scheduled handler exists. Reserved emptying command IDs and custom-action aliases are blocked from agent proposals. Saved grants and `confirmTrash: false` cannot skip this boundary. The latter setting affects ordinary Move to Trash only.

The footer centers **Empty Trash…**, with the item count left and Refresh/Done right. Its button ignores synthetic clicks. On macOS it directly presents a native alert naming the item count, including folder contents, stating permanence, and defaulting Return to Cancel. The affirmative button has no key equivalent. Only the alert's private affirmative continuation can proceed; the binding exposes no callable erasure or confirmation response. It verifies known system Trash roots, owner and identity, then inventories their complete trees on a background queue. Before the first removal it checks the complete inventory again. Handle-relative `openat`, `fstatat` and `unlinkat` keep every operation inside the reviewed Trash; symlinks are never followed, mount/device changes are rejected, and `F_GETPATH` rejects a folder moved outside Trash. Roots themselves are never removed. Budgets cap review depth, item count and open roots. A later failure stops remaining work and reports it; no force-removal fallback exists.

Windows and Linux retain a private continuation after native confirmation with Cancel as default, followed by an inventory recheck. Windows calls [SHEmptyRecycleBin](https://learn.microsoft.com/en-us/windows/win32/api/shellapi-shemptyrecyclebinw) with its own confirmation retained; it never passes `NOCONFIRMATION` or `-Force`. Linux calls the fixed GIO Trash operation, with no filesystem-removal fallback. These adapters require supported-platform native qualification before release. This boundary governs Viewer API/agent capabilities; it does not sandbox unrelated programs with their own OS permissions.

Checks cover read-only service behavior, unsafe roots, changed inventory, permission failure, exact picker destinations, blocked aliases, sorting, metadata identity/version matching and public erasure-method absence. The native C++ guard runner replaces every `unlinkat` with a recording no-op. Owned native renderer tests use stub Trash operations and generated-file previews; separate native tests read date-added metadata and restore only generated private-root items. Actual system Trash emptying and affirmative native confirmation have not been performed or approved by the agent. The earlier direct-app read-only check encountered macOS privacy denial; positive post-grant system Trash browsing/restoration, physical assistive technology, Windows/Linux runtime and signed Store access remain pending. All generated profiles, captures and fixtures are preserved until their removal is explicitly approved. Current evidence is recorded in [verification](verification.md#trash-navigation-sorting-and-metadata-refinement-october-14).
