# Trash and Applications

The sidebar's Applications button opens `/Applications` on macOS, the configured Program Files directory on Windows, and `/usr/share/applications` on Linux. It browses the directory; it does not claim to aggregate all installed applications.

Trash opens a dedicated read-only inventory, named Recycle Bin on Windows. It does not navigate an ordinary writable folder plane or expose its items to generic file commands. macOS reads the actual user's `.Trash` and mounted-volume `.Trashes/<uid>` folders. Linux discovers the home and mounted-volume locations defined by the [freedesktop Trash specification](https://specifications.freedesktop.org/trash/1.0/); original locations come from checked `.trashinfo` files. Windows enumerates the [Shell Recycle Bin namespace](https://devblogs.microsoft.com/oldnewthing/20140421-00/?p=1183). Original-location columns appear only when that metadata is available. Restore, preview and individual permanent removal are not included in this extension.

The inventory checks private ownership, permissions and canonical roots. It never follows a Trash-root symlink. Missing roots are skipped; unreadable roots are reported as unavailable, not empty. The list is capped at 4,000 visible items and virtualized. Partial or unreadable inventories disable emptying. Reading and refreshing never call removal. macOS requires Full Disk Access to enumerate system Trash; a folder picker cannot grant this privacy permission. Privacy denial explains System Settings → Privacy & Security → Full Disk Access, enabling Viewer and restarting it. Open Privacy Settings… opens a fixed settings URL only; Viewer does not grant permission or widen agent scopes. [Apple's macOS security guidance](https://developer.apple.com/videos/play/wwdc2019/701/?time=1995).

App Sandbox file authorization is independent of Full Disk Access. An explicit `FILE_ACCESS_REQUIRED` result offers the exact private Trash folder picker, with hidden folders shown and Command-Shift-G path instructions; choosing a different folder never grants it. Unverified/symlink roots offer no access action. Genuine signed Store access remains unqualified. Apple documents that [Trash URLs differ in an App Sandbox](https://developer.apple.com/documentation/foundation/url/trashdirectory); Viewer does not substitute the container's Trash for the user's system Trash.

`trashList`, `trashAccess` and `trashMenu` are the entire renderer interface. `trashMenu` can display native UI only. It accepts the revision of the last inventory, not paths, an actor, an approval flag, an empty operation or a callback. No `emptyTrash`, erasure/approval IPC, command registration, shortcut, MCP tool, recipe or scheduled handler exists. Reserved emptying command IDs and custom-action aliases are blocked from agent proposals. Saved grants and `confirmTrash: false` cannot skip this boundary. The latter setting affects ordinary Move to Trash only.

On macOS, **Trash actions → Empty Trash…** selects a native `NSMenu` item. Only its private action callback prepares and confirms erasure. A native alert always names the item count, includes folder contents, states permanence, and defaults Return to Cancel. The affirmative button has no key equivalent. The binding exports only menu display, with no callable erasure or confirmation response. It verifies known system Trash roots, owner and identity, then inventories their complete trees on a background queue. Before the first removal it checks the complete inventory again. Handle-relative `openat`, `fstatat` and `unlinkat` keep every operation inside the reviewed Trash; symlinks are never followed, mount/device changes are rejected, and `F_GETPATH` rejects a folder moved outside Trash. Roots themselves are never removed. Budgets cap review depth, item count and open roots. A later failure stops remaining work and reports it; no force-removal fallback exists.

Windows and Linux use private Electron native-menu callbacks and a native confirmation with Cancel as default, followed by an inventory recheck. Windows calls [SHEmptyRecycleBin](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shemptyrecyclebinw) with its own confirmation retained; it never passes `NOCONFIRMATION` or `-Force`. Linux calls the fixed GIO Trash operation, with no filesystem-removal fallback. These adapters require supported-platform native qualification before release. This boundary governs Viewer API/agent capabilities; it does not sandbox unrelated programs with their own OS permissions.

Checks cover read-only service behavior, unsafe roots, changed inventory, permission failure, exact picker destinations, blocked aliases and public erasure-method absence. The native C++ guard runner replaces every `unlinkat` with a recording no-op: generated fixtures and an outside sentinel remain intact. Actual native emptying and confirmation interaction have not been performed or approved by the agent. The local direct-app read-only check encountered macOS privacy denial; positive post-grant browsing and signed Store access remain pending. All generated profiles, captures and fixtures are preserved until their removal is explicitly approved.
