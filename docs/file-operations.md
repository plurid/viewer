# File operations and recovery

Ordinary file actions share one desktop operation queue. New folder, rename, duplicate, copy/move, native Trash, ZIP creation and archive extraction report progress through the operations popover. **Recent file operations** opens retained history from Commands or the File menu. A job can finish with some completed items and some errors; inspect both rather than assuming the whole selection succeeded. Reviewed plans, agent changes and Trash restores run after the work already queued, in the order it was asked for, so an unanswered collision prompt holds them until it is answered. Undo can also run while a job waits at its prompt, when neither that job nor a queued one involves the items it puts back (their folders included); the job goes on once Undo has ended. Asking for the same Undo again while it waits joins it. Ejecting a volume or revoking a folder's access cancels the jobs that involve it and waits only for one of those in progress, not for unrelated work or its prompts.

## Transfers and conflicts

Selected descendants are carried by their selected parent once. Same-volume moves publish the original filesystem object with an exclusive rename. A drag or drop (a transfer) moves only when the source and the resolved destination folder share a volume, so dropping onto a link to a folder on another volume copies. Copies and cross-volume moves stream through a private staging location; source identity, size and modification are checked before publication. A file appearing at the destination during the job is not silently overwritten.

Conflicts offer Skip, Keep both, Replace or Cancel. Replace moves the existing destination to native Trash only once its replacement is staged and ready, immediately before publication; it is a distinct mutation recorded in the receipt. If publication then fails, the replaced item is put back when its original location is still free. Replace is pinned to the item shown in the prompt: a destination changed while the prompt was open is kept, and the item fails with an explanation. Reviewed sources are checked again once a collision is decided and inside the claim that publishes them, so a source edited while its prompt was open is neither copied nor moved. Replace is not offered when the existing item contains the source, or for New Folder. A destination that is another spelling of the source itself (case or Unicode variant, symbolic-link or firmlink folder) is identified by device and inode: copying it creates a copy, and other operations stop as the same item. Cancellation stops later work and cleans owned staging, while completed items remain visible in history. An unavailable source/destination permission stops the affected operation. In the Store edition, source and destination need their own applicable native grants; a JSONC path is not authorization.

On macOS, copying preserves modes, timestamps, xattrs, resource forks, ACLs and relative links through the native adapter. Unsupported metadata is reported as an error. Cross-volume move removal is restricted to the validated copied entries. If the source changes or removal fails, the completed destination and remaining original items are retained with an error. Same-volume rename/move and cross-volume copy/move have different recovery possibilities.

Protected folders cannot be moved to Trash, moved, renamed or replaced by any request, including recipes, agents and watch rules: the disk root, Home and its standard folders (Desktop, Documents, Downloads, Library, Movies, Music, Pictures, Public, Applications) and system locations such as `/Applications`, `/System`, `/Users` and `/Volumes`. Matching uses device and inode, so other spellings are protected too; items inside these folders are unaffected (`desktop/protected-paths.ts`).

Staging cleanup never deletes user-visible data. An emptied staging folder is removed with `rmdir`. Partial content left by a failed or cancelled transfer is renamed `Viewer incomplete transfer …` and moved to native Trash; where no Trash is available it is kept and listed in the job's errors. Permanent removal in the desktop process is limited to `desktop/removal.ts`, and ESLint rejects `rm`, `rmdir` and `unlink` elsewhere.

The Trash confirmation lists selected folders' full contents (file and folder counts and size), measured read-only in the background while the dialog is open; Enter still confirms immediately. **New folder with selection…** (⌃⌘N) creates a folder beside the selected items and moves them into it as two ordinary jobs, each with its own Undo; the move targets the folder actually created and only the items as they were chosen.

## Selecting

Drag across blank space in list or grid view to select the items under the rectangle. Hold Shift or Command to add them to the current selection. The view scrolls when the pointer nears its top or bottom edge, and the click that ends the drag keeps the selection. Rows outside the visible window are selected too, by their measured positions.

**Select by pattern** (⌃⌘=) and **Deselect by pattern** (⌃⌘-) open the command line at `select ` or `deselect `. Each takes either globs, one per word and any matching (`*.md *.txt`, `IMG_????.jpg`), or a file query (`ext:md modified<7d`; see [search.md](search.md)). The matching items in the folder plane are added to the selection, or taken out of it.

## A commander's pair

Two folder planes can work as Norton or Midnight Commander's two panels:
- **Pairing.** **View side by side** and **View stacked** pair the two planes they show. **Pair with…** labels the planes in view and pairs the one you choose. A paired plane shows ⇄ beside its title.
- **Copying and moving.** **Copy to …** (⌃⌘C, prefix `>`) and **Move to …** (⌃⌘X) send the selection to the other folder. They use the same transfers, conflicts and Undo as Paste. The keys are ⌃⌘ with copy's and cut's letters rather than F5 and F6.
- **Moving between the two.** **Swap the pair's folders** (prefix `<`) trades them. **The other folder of the pair** (prefix Tab) makes the other plane active.
- **Following.** **Follow each other into folders** makes the two go into the same subfolder together, and back up together; ⇉ shows it. A jump elsewhere stays one plane's own, and a subfolder the other folder lacks is said, not made.
- **Unpairing.** **Unpair** ends the pair, and so does closing either plane.

## Creating

New file… (Folder menu) creates an empty file through the operation service, exclusively: a name that already exists can only keep both or be skipped, never replaced. Undo moves the new file to the Trash. New folder follows the same rule.

## Saving text

A text file edited in its preview plane saves through the operation service (`Operations.writeText`, 2026-10-23). The first save of an editing session is a **Save** job (`rewrite`): the text is staged privately beside the file with its tags, extended attributes and mode, the version it replaces is moved to the Trash pinned to the version the editor read, and the staged file takes its place. Undo moves the saved version to the Trash and puts the replaced one back. Later saves in the same editing session overwrite what that session wrote (`desktop/text-files.ts`), checked by hash against it; a relaunch or a new editing session sends the next replaced version to the Trash again. A save is refused, with Reload, Save Over It or Cancel, when the file changed on disk since it was read; Save Over It moves the changed version to the Trash. Saves run beside the queue's work, never behind another job's collision prompt, and Eject or a revoke waits for them. The text is never journaled, only its SHA-256 and length, so a save is not offered for Redo.

Only UTF-8 text without NUL bytes, of up to 4 MiB, in a regular file with no other hard link and a writable file and folder, is edited in place: a save puts a new file in its place, which would separate a hard link from its other names. A symbolic link is edited at the file it points to. The byte-order mark and the file's line breaks are kept. Save As (⇧⌘S) asks where to save, starting on the Desktop: a new name is created exclusively (**New file**, which Undo moves to the Trash); replacing an existing file moves it to the Trash first, whatever it holds.

## Quick actions

The Quick actions submenu works on selected images (JPEG, PNG, TIFF, HEIC, GIF, BMP, WebP):

- Rotated copy, left or right
- Convert copy to JPEG or PNG
- Create PDF from images, one page per image in selection order

Each action creates a new file next to its source and never changes the source. Outputs are written to a private stage, published exclusively, and resolved like any new file (keep both, skip or replace). Undo moves them to the Trash. Images are decoded by the system image reader inside Viewer, so the actions work in the App Store build. Copies are re-encoded (JPEG at quality 92) and do not carry the source's metadata. Images over 100 megapixels are refused.

## Duplicates

**Find duplicates…** searches selected folders (or the current one) for files with identical contents. It never follows links, compares only regular files of the same size, filters on the first 64 KB and confirms with full SHA-256; hard links to one file count once, because removing one frees nothing. The search is read-only, cancellable and bounded (100,000 files, five minutes). Nothing is chosen at first, and the last copy in a group cannot be chosen; chosen copies go to an ordinary reviewed operation plan, so moving them to Trash pins their versions, honours protected folders and keeps Undo.

## Archives

**Compress as ZIP…** creates a ZIP outside the selected source trees. Creation accepts up to 20,000 entries and 2 GiB of input. Files stream into the staged output, so this limit does not imply loading the entire selection into memory. Source changes, unsupported special entries and conflicting archive names stop creation.

**Extract archive…** handles ZIP, TAR and TAR.GZ/TGZ. ZIP names are read as their archiver wrote them: UTF-8 when the format's flag or an Info-ZIP Unicode Path field says so, or when the bytes are valid UTF-8 (as macOS writes them without the flag), and CP437, the format's default, otherwise. Each selected archive extracts into a named folder in the chosen destination, through private staging before publication. Limits are 20,000 entries, 32 MiB per file and 256 MiB total extracted contents; TAR/gzip parsing has its additional preview/decompression limits. Unsafe absolute/parent paths, Unicode/case name conflicts, encrypted entries, links and special entries are rejected. Extracted folders/files use private permissions (`0700`/`0600`); archive executable modes, timestamps and extended metadata are not restored. Extraction does not fetch remote assets or expand nested archives recursively. Archive previews remain read-only entry viewers; they do not extract files merely by opening an entry.

## Undo and restart

Edit ▸ Redo (⇧⌘Z) starts an undone operation again as a new job with every usual check, pinned to the versions Undo restored, so it cannot act on a different file that later appeared at the same path. Starting another operation ends the Redo offer, and it does not survive a restart. Command-Z and operation history offer Undo only when a durable receipt and current filesystem state make it eligible. Rename/same-volume move restore their original location; copied/created/archive outputs require an unchanged output tree; Viewer Trash receipts restore their recorded item (one already put back from the Trash browser takes its receipt with it, so its Undo is no longer offered). Changed output contents, occupied restoration paths, missing permissions or an output beyond the bounded proof budget can prevent Undo. Cross-volume moves currently have no application Undo. Layout arrangement Undo is separate from file Undo. The output proof covers each entry's device, inode, size, modification and change times and mode, so a metadata-only change (a tag, a quarantine flag, a permission change, a Finder `.DS_Store` added to a trashed folder) also makes Undo unavailable. A reviewed folder is pinned by its own entry, which nested edits do not change; only an agent's approved Trash also pins the folder's contents.

Receipts are written before filesystem transitions and retained in the private app profile. Completed eligible jobs can survive graceful Quit and relaunch. Interrupted mutations are retained with recovery paths for inspection; they are not replayed automatically, and an interrupted Undo is not offered again, whether the job it was undoing had completed, failed or been cancelled. Quit with file operations in progress asks first: **Wait for them** finishes them, then quits (Viewer reopens its window if it is closed, so their questions can be answered), **Cancel them and quit** cancels them and waits for them to settle, and **Keep Viewer open** quits nothing. Preserve the original, destination and any reported staging/recovery path until their contents have been reviewed.

A terminal failure stores recovery paths separately from an in-flight mutation intent. Relaunch preserves its recorded status/errors and eligible Undo for successfully completed items; it does not relabel a known failure as an interrupted Undo. A final journal-save failure is reported even when the output copy completed, and the original and completed output are retained. Actual interrupted transitions still require inspection and are never replayed automatically.

Receipts live in `operation-journal-v2/`, one append-only log per job (`desktop/operation-journal.ts`). Each checkpoint appends and syncs only what changed — status, intent, new completed items, errors and Undo steps — so writing a long job's receipts grows linearly rather than with the square of its length, and a finished job is compacted to one line by an atomic rename. A torn final line left by a crash is ignored, because no file change followed it, and the log is rewritten whole before anything is appended after it; any other unreadable log is renamed `.unreadable-<time>` with a notice, and other jobs and file operations continue. A version 1 journal is converted on first launch and kept as `operation-journal-v1.json.migrated-<time>`. A completed Trash whose Undo record cannot be saved is reported as moved to Trash with Undo unavailable, rather than as a failure; so is a trashed folder of more than 10,000 items, which is too large to check before putting it back. Every job is journaled however many are queued: a checkpoint records the running job and every job whose state changed. History keeps the latest 100 finished jobs, and pending work never counts toward or is discarded by that bound; each job holds up to 10,000 items and 30,000 Undo steps (Replace adds one per item). It is an application recovery mechanism, not a backup or a general browser for all items in macOS Trash. Recipe proposals have their own reviewed recovery behavior, documented in [actions](actions.md).

## Qualification boundaries

Generated signed-runtime checks cover local metadata fidelity, native Trash receipts, cold restoration and owned-resource cleanup. Native low-space/interruption/provider failure, genuine separate picker roots and real Finder transfer intent remain release acceptance requirements. Full coordinated cloud/file-provider I/O is unfinished. See [release qualification](release-qualification.md) and the exact [native acceptance scenarios](release/native-acceptance.md) before making a distribution claim.
