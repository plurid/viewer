# Mac App Store readiness

Assessed October 12, 2026, for Viewer 0.1.0. Scope: the active Electron application, packaged Apple Silicon bundle, native helpers, file access, commands/terminals, model requests, agent transport, release metadata and repository verification. Source and local binary findings are distinguished from work that needs a signed sandboxed build or App Review.

**Status: the product can pursue the Mac App Store, but the current installer is not a Store submission.** Electron supports a separate MAS runtime and submission workflow. A normal `darwin` bundle cannot be made equivalent merely by adding sandbox entitlements. Store development and distribution builds need the appropriate certificates and provisioning profiles. [Electron submission guide](https://www.electronjs.org/docs/latest/tutorial/mac-app-store-submission-guide).

The largest engineering risks are persistent filesystem access and the subprocess/agent features. Successful local tests of the existing app do not establish that these work inside Apple's App Sandbox. The Store requires sandboxing, self-contained installation and Store-managed updates; background processes also need appropriate user consent. [App Review Guidelines, 2.4.5](https://developer.apple.com/app-store/review/guidelines/#hardware-compatibility).

Electron exposes picker bookmarks and a paired access/release API for Store builds. Access should be scoped to the lifetime of the corresponding file work. [Electron dialog API](https://www.electronjs.org/docs/latest/api/dialog), [Electron app API](https://www.electronjs.org/docs/latest/api/app#appstartaccessingsecurityscopedresourcebookmarkdata-mas).

Embedded tools must participate in the containing app's sandbox. Static inheritance does not automatically include access subsequently obtained through the file picker. This matters directly to the OCR, indexing and PTY workers. [Apple sandbox inheritance reference](https://developer.apple.com/library/archive/documentation/Miscellaneous/Reference/EntitlementKeyReference/Chapters/EnablingAppSandbox.html), [Apple helper-tool guidance](https://developer.apple.com/documentation/xcode/embedding-a-helper-tool-in-a-sandboxed-app).

Apple requires an accessible privacy policy and explicit permission before sharing personal data with third-party AI. These requirements also matter when the transmitted data is a filename rather than document content. [App Review Guidelines, 5.1.1–5.1.2](https://developer.apple.com/app-store/review/guidelines/#privacy). Privacy manifests must describe relevant API/data use; macOS app manifests belong in `Contents/Resources`. [Apple manifest guidance](https://developer.apple.com/documentation/bundleresources/adding-a-privacy-manifest-to-your-app-or-third-party-sdk).

## Findings addressed in this pass

- Main-window frame persistence now captures native moves/resizes, including Rectangle's ordinary-window enlargement. Final geometry is flushed before Close/Quit. Restore retains the last size/position, follows a changed monitor's work area and recovers onto the primary display if the old display is absent. Minimized geometry is ignored; maximize/fullscreen use the normal frame plus their mode flags. State is validated, reads are bounded and writes use a private atomic replacement. Failed saves can retry at close.
- The packaging audit found the signer's default camera, microphone, Bluetooth, USB, location, Photos and print entitlements in the local bundle. The build now explicitly uses the JIT-only entitlement file and removes unsigned executable-memory permission. This reduces unnecessary entitlements; it does not turn the build into an Apple sandboxed or notarized release.
- Store engineering now has separate runtime/signing channels, fail-closed certificate/profile validation, private picker-grant persistence and canonical file boundaries. Index configuration skips ungranted roots without rewriting user preferences, and cached index rows remain invisible until a permitted scope is configured. Opening a restricted folder requests access rather than presenting it as empty. Reader permission codes survive worker/preload boundaries.
- The read-only CT Dentar EAS build inventory confirms a completed production iOS Store build for `ro.ctdentar.app`, build 7. Its remote build does not supply a local Viewer macOS development profile. No EAS credentials were exported or changed; the interactive configuration flow was stopped after automatic approval review rejected profile selection.
- The owner created and installed Propal's Apple Development certificate through Apple Developer and Keychain. The agent verified public certificate metadata and private-key availability. With explicit approval for the registration correction and additional annual slot, the agent registered this Mac's Provisioning UDID, disabled the incorrect Hardware UUID entry and regenerated Viewer Development with only the correct device. The owner's replacement download passes local preflight and is embedded unchanged in the rebuilt signed app. No private key was exported, no device identifier/profile was written into repository configuration, and no Store upload was performed.
- The signed Apple Silicon MAS development baseline is established: strict signatures pass before and after copying the app, main sandbox/app/group/debug entitlements match, and Electron/login/Swift helper entitlements contain only sandbox and inheritance rights. `pnpm test:mas` passes real startup, the initial permission request, actual home paths, private container configuration, ungranted file/folder denial, closing/creating planes and graceful Quit. Native picker grants, bookmark restoration, terminals and external MCP still need signed acceptance.
- The Home indexing `EMFILE` regression is reproduced and fixed with native directory watches. The signed MAS test indexes 2,304 generated files under a 512-handle limit using 62 handles, verifies state saves and live nested add/rename/delete updates, and retains native permission denial. Sidebar/Places navigation now requests access for denied folder destinations such as Volumes; cancellation and acceptance pass a generated browser scenario. Physical-drive grants and cold bookmark restoration are not established by that simulation.

## Existing strengths

The production renderer disables Node integration, enables context isolation/Chromium sandboxing, denies external navigation/window creation and uses a restrictive local-resource CSP. IPC validates trusted callers and arguments. Packaging disables RunAsNode, Node options and CLI inspection, enables ASAR integrity and loads application code from ASAR. Credentials use Electron safe storage on explicit save/use. Local agent sockets/authentication files have restrictive permissions; native filesystem identity checks, reviewed changes, conflict handling and Undo have regression coverage.

The current production-dependency registry audit completed with zero known advisories across 162 dependencies. Electron is declared as a development dependency and is not covered by that production-only check; Chromium/native/WASM internals need their own release inventory and security review.

These are source/binary observations and test evidence, not a security certification. Custom processes in the current direct build run with the user's OS permissions. Working-directory selection and application grants do not contain them. Agent clients currently share one authentication/grant set.

## Implementation order and acceptance gates

1. **Create a signed MAS development baseline.** Package with the MAS runtime and explicit main/helper entitlements; validate code signatures, the profile and entitlement inventory. Launch on a registered test Mac. Keep direct-download packaging separate. A signed development baseline is needed before claiming any sandbox feature works.
2. **Implement persistent native file permissions.** Cover first-plane/default locations, picker cancel/denial, workspace restore, Favorites, external volumes, drag/drop/open-file events, previews and their adjacent assets, indexing/OCR, watchers, copy/move/rename/Trash and Undo. Test grant revocation, stale bookmarks, relaunch and operations across two independently granted roots. Prefer an actionable permission request over an unexplained unavailable-folder error.
3. **Resolve terminal/custom-command/agent parity with evidence.** Exercise actual packaged PTYs, signals, cleanup, external terminal handoff and tmux; verify external MCP authentication and file boundaries from a separate process. An enabled terminal must not imply arbitrary filesystem access. If a feature cannot operate appropriately under the sandbox, document the exact limitation and agree the Store product behavior before changing it.
4. **Complete privacy and distribution records.** Test disclosure/permission before every relevant cloud request, revocation, key removal, local-only mode and network failure. Validate privacy manifests against the binary inventory, complete dependency notices, prepare review instructions and finalize Store metadata/export answers. The separate direct-download release needs Developer ID signing, hardened-runtime validation and notarization; the current local DMG provides none of those public-distribution assurances.
5. **Run release validation.** Test both the minimum supported macOS and the current shipping release, intended CPU architectures, clean install/update, granted/denied access, disconnected displays/drives and a non-development profile. Validate/upload the Store submission through Apple's tooling, resolve validation findings, and submit only after the reviewable build and listing are approved. Apple makes the final review decision.

Recommendation from this audit: retain the complete direct-download product while proving a sandboxed Store build. A single feature-complete Store product may be possible, but the subprocess and cross-process access work needs evidence first. No features were removed during this audit.
